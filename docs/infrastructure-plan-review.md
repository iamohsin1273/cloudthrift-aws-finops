# Offline infrastructure plan review

These plans were generated on 2026-11-24 by `terraform test -verbose` with the Terraform mock AWS provider and `command = plan`. They use synthetic account ID `123456789012`, the default dev settings, and an example state bucket. They make no AWS API calls, create no cloud resources, and cannot be applied. They do not inspect real account state, existing names, permissions, quotas, regional availability, pricing, or backend access. A real plan with the intended account, backend and final configuration is required before any apply.

- [Bootstrap mock plan](offline-bootstrap-plan.txt): 6 additions for the state bucket, public access block, versioning, encryption, ownership controls and HTTPS-only bucket policy. The example bucket name must be replaced by a unique name.
- [Dev mock plan](offline-dev-plan.txt): 14 additions: 7 report-bucket resources, 4 collector resources, and 3 scheduler resources. The collector defaults to Python 3.12, 256 MB, 300 seconds, reserved concurrency 1 and 14-day logs. The scheduler defaults to 06:00 Asia/Kolkata, with two delivery retries and a one-hour event age. Reports have a 365-day expiration and noncurrent versions expire after 30 days.

The mock provider returns an **empty synthetic IAM policy** for data sources it cannot evaluate, and some resource IDs and outputs are unknown. Those policy contents in the mock plan must not be used as a security review or copied into deployment. Review the actual Terraform sources: the collector can query Cost Explorer, describe EC2, identify its account, write under the report prefix and write to its log group. The scheduler can invoke the collector. Data-source policies are rendered by the real provider when a real plan is made. Neither role authorizes EC2 changes. IAM resource wildcards for Cost Explorer and EC2 describe are required by those APIs; scoped report and log permissions depend on generated ARNs.

Remaining review points: report tags may be sensitive; buckets have no access logging or customer-managed KMS key; no DLQ or alert is configured; and neither trust policy currently constrains the AWS service principal with source-account/source-ARN conditions. Evaluate these against the intended account and threat model before deployment. The state bucket starts with local bootstrap state and needs controlled access and a recovery procedure. Review all security scan findings and actual policies before applying.
